## Первичный анализ

Начал с изучения исходного кода бэкенда, так как в подобных заданиях логика авторизации обычно и содержит уязвимость.

Из кода стало ясно, что **флаг выдаётся только в том случае, если пользователь является администратором** — проверка завязана на поле `is_admin` внутри JWT-токена пользователя.

В коде нашлись две ключевые функции:
- функция **создания** токена (выдаётся обычному пользователю при логине, `is_admin: false`);
- функция **верификации** токена (`verify_token`), вызываемая при каждом аутентифицированном запросе.

Сравнив обе функции, я заметил несоответствие: при **создании** токена поле `jku` нигде не используется и не выставляется сервером. Но при этом функция **верификации** токена явно умеет его читать и обрабатывать — сервер самостоятельно проверяет, не передан ли в заголовке токена `jku`, и если да, обращается по этому URL за ключом.

Такое расхождение — явный звоночек: если сервер готов обрабатывать поле, которое сам никогда не выставляет, значит это потенциальная точка для подмены со стороны клиента.

## Эксплуатация

### Суть уязвимости

Уязвимость, которую я проэксплуатировал — **`jku` Header Injection** 

Её суть в следующем: вместо того чтобы проверять подпись JWT-токена фиксированным, заранее известным публичным ключом сервера, бэкенд **доверяет ссылке `jku`, указанной в заголовке самого токена**, и сам идёт по этой ссылке за ключом для проверки подписи.

Поскольку `jku` полностью контролируется атакующим, появляется возможность:

1. Сгенерировать собственную пару RSA-ключей.
2. Опубликовать свой **публичный** ключ в формате JWKS (`{"keys": [...]}`) на любом доступном серверу ресурсе.
3. Подписать произвольный токен (с `is_admin: true`) своим **приватным** ключом.
4. Указать в заголовке токена `jku`, ведущий на свой опубликованный ключ.

Когда сервер получает такой токен, он видит заголовок `jku`, доверчиво скачивает оттуда ключ — тот самый публичный ключ, который сгенерировал атакующий, — и проверяет им подпись. Подпись сходится, потому что подписывал токен тем же самым ключом атакующий. В результате сервер принимает полностью поддельный токен как легитимный.

### Пошаговая эксплуатация

**1. Поднял собственный сервер и пробросил его в интернет**

Запустил локальный HTTP-сервер (`python3 -m http.server`) и пробросил его наружу через **ngrok**, получив публичный URL, доступный серверу таргета.

**2. Сгенерировал RSA-пару ключей**

Создал собственную пару приватного и публичного ключей с помощью библиотеки `cryptography`. Приватный ключ остаётся только у меня — им я буду подписывать токен. Публичный ключ пойдёт в JWKS-файл, который будет отдавать мой сервер.

**3. Собрал JWKS-файл и опубликовал его**

Преобразовал публичный ключ в формат JWK, присвоил ему `kid` (Key ID), обернул в структуру `{"keys": [...]}` и сохранил как `jwks.json` в папке, которую раздаёт мой сервер.

![Публичный ключ в формате JWKS](./images/image3.png)
*Содержимое jwks.json, отданного по ngrok-ссылке*

**4. Сформировал и подписал поддельный токен**

Создал JWT со следующими параметрами:

- **Header:**
```json
  {
    "alg": "RS256",
    "typ": "JWT",
    "kid": "key-1",
    "jku": "https://<мой-ngrok-url>/jwks.json"
  }
```
- **Payload:**
```json
  {
    "sub": "admin",
    "is_admin": true,
    "iat": 1791277825,
    "exp": 1791287825
  }
```

Подписал его своим приватным ключом алгоритмом `RS256`.

![Сгенерированный токен](./images/image4.png)
*Готовый токен с подменённым jku и правами администратора*

**5. Отправил токен на сервер**

Осталось передать полученный токен серверу в заголовке авторизации:

```bash
curl -H "Authorization: Bearer <forged_token>" http://TARGET/
```

Сервер обработал заголовок `jku`, скачал мой публичный ключ, успешно проверил подпись и принял `is_admin: true` как валидное утверждение — после чего вернул флаг.

![Полученный флаг](./images/image5.png)
*Успешная эксплуатация — флаг получен*

## Способы защиты от `jku` Injection

1. **Не использовать `jku` вовсе.** Если список ключей сервера статичен и известен заранее — нет смысла позволять токену указывать, откуда брать ключ для его же проверки.

2. **Жёстко фиксировать допустимый алгоритм подписи** в коде верификации (например, явно разрешать только `RS256`), не полагаясь на значение `alg` из самого токена, и исключить возможность `alg: none`.

3. **Если `jku` действительно необходим по архитектуре** (например, в федеративных системах с несколькими доверенными издателями) — обязательно:
   - **Отключить автоматические редиректы** при запросе по `jku`, чтобы нельзя было обойти проверку домена через 3xx-переход на произвольный хост;
   - **Вести allowlist доверенных доменов**, разрешая запрос ключа только по заранее одобренным источникам;
   - **Блокировать запросы на локальные и приватные подсети** (`127.0.0.1`, `10.0.0.0/8`, `169.254.0.0/16` и т.д.), чтобы `jku` нельзя было использовать как вектор для SSRF.
