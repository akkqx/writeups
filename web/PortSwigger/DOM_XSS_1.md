## Входные данные

Дан сайт сайт форума из лабы PortSwigger, и дана подсказка, касаемо уязвомости — DOM-based XSS.
Задача лабы — выполнить XSS-атаку, вызывающую `alert(1)`.

---

## Разведка

### 1. Поиск скриптов на странице

Потыкав разные эндпоинты, на странице с эндпоинтом `/?search=` заметил интересный скрипт — функцию `trackSearch`, которая подставляет поисковый запрос в картинку-треker (`tracker.gif`) через `document.write`:

```html
<script>
    function trackSearch(query) {
        document.write('<img src="/resources/images/tracker.gif?searchTerms='+query+'">');
    }
    var query = (new URLSearchParams(window.location.search)).get('search');
    if(query) {
        trackSearch(query);
    }
</script>
```

### 2. Анализ source → sink

Разобрал скрипт по цепочке **source → sink**:

```
location.search
    → URLSearchParams.get('search')   // source: данные из URL, контролируемые атакующим
    → trackSearch(query)
    → document.write('<img src="...?searchTerms=' + query + '">')  // sink: запись в DOM/HTML
```

Ключевые наблюдения:

1. **Source — `location.search`.** Значение берётся из URL страницы (`?search=...`). Значит, атакующий полностью контролирует его, просто отправив жертве ссылку с нужным параметром. Сервер в этом процессе вообще не участвует.
2. **Sink — `document.write()`.** Функция записывает строку прямо в HTML-документ как разметку. Всё, что попало в эту строку, браузер интерпретирует как HTML, а не как текст.
3. **Нет экранирования.** `query` конкатенируется в строку без какой-либо очистки. Если в значении есть кавычка `"`, можно выйти из атрибута `src` у тега `<img>` и внедрить свой HTML/JS.

Именно это и есть **DOM XSS**: уязвимость живёт целиком на стороне клиента — данные не отправляются на сервер и не обрабатываются им, а обрабатываются JavaScript в браузере жертвы.

## Эксплуатация

Ввёл в поиск случайную строку и через *Inspect* убедился, что она попадает внутрь атрибута `src` у `<img>`:

```html
<img src="/resources/images/tracker.gif?searchTerms=...">
```

Теперь ломаю контекст атрибута: закрываю кавычку, закрываю тег `<img>` и внедряю свой тег с обработчиком события:

```
"><svg onload=alert(1)>
```

Итоговый URL:

```
https://<lab-host>/?search="><svg onload=alert(1)>
```

Что происходит при открытии такой ссылки:

1. `location.search` = `?search="><svg onload=alert(1)>`
2. `query` = `"><svg onload=alert(1)>`
3. `document.write()` записывает в страницу:

   ```html
   <img src="/resources/images/tracker.gif?searchTerms="><svg onload=alert(1)>">
   ```

4. Браузер парсит это как: закрытый атрибут `src`, закрытый тег `<img>`, затем новый тег `<svg>` с обработчиком `onload`.
5. При загрузке SVG срабатывает `onload` → выполняется `alert(1)`. Лаба засчитана.

> **Примечание про мой первый payload.** Изначально я пробовал:
>
> ```
> /?search='"><script>alert(1)</script>
> ```
>
> Он тоже сработал, но официальный и более надёжный вариант — через `<svg onload=...>`: он не требует закрывать тег и не зависит от особенностей парсинга `<script>` внутри `document.write`. Ведущий `'` в моём payload вообще лишний — из атрибута выходит именно `"`.

## Риск уязвимости

- **DOM XSS в функционале поиска.** Атакующий может отправить жертве вредоносную ссылку — при её открытии в браузере жертвы выполнится произвольный JavaScript в контексте сайта.
- Последствия классические для XSS: кража сессионных данных (если они доступны из JS), подмена содержимого страницы, фишинг от имени доверенного сайта, действия от имени пользователя.
- Уязвимость особенно коварна тем, что **серверные фильтры и WAF её не видят**: вредоносный payload никогда не отправляется на сервер, он живёт только в URL и обрабатывается на клиенте. Защита только на бэкенде здесь не сработает.
- `document.write()` — опасный sink по определению: он интерпретирует вход как HTML-разметку, поэтому любой неэкранированный пользовательский ввод в нём превращается в XSS.

Severity — **Medium** (для лабы): эксплуатация тривиальна и не требует аутентификации, но для полноценного ущерба нужен переход жертвы по вредоносной ссылке.

## Меры по исправлению

1. **Не использовать `document.write()` с пользовательскими данными.** Для динамического создания элементов использовать DOM API:
   ```js
   const img = document.createElement('img');
   img.src = '/resources/images/tracker.gif?searchTerms=' + encodeURIComponent(query);
   document.body.appendChild(img);
   ```
   Присвоение через свойство `src` не парсится как HTML, поэтому инъекция разметки невозможна.
2. **Экранировать/кодировать вывод** под конкретный контекст (HTML, атрибут, JS, URL). Для URL-параметров — `encodeURIComponent()`, для HTML — экранирование `& < > " '`.
3. **Не доверять данным из `location.search` / `location.hash`** — это полностью контролируемый атакующим источник. Любой такой ввод нужно валидировать и кодировать перед попаданием в DOM.
4. **Content Security Policy (CSP)** как дополнительный слой защиты: политика `script-src` ограничит выполнение инжектированного кода даже при наличии бага.
5. **Аудит клиентского JS** на предмет опасных sink'ов: `document.write`, `innerHTML`, `outerHTML`, `document.writeln`, `insertAdjacentHTML` и т.п. — все места, где данные из source'ов попадают в DOM без кодирования.

## Чему я научился

- Наконец-то понял, что такое DOM XSS: уязвимость, которая полностью происходит на стороне клиента — source и sink находятся в JavaScript, а сервер не участвует в цепочке вообще.
- Понял, как работает цепочка `location.search → URLSearchParams.get() → document.write()` и почему `document.write` считается опасным sink'ом.
- Увидел, что payload через `<svg onload>` надёжнее, чем через `<script>`, и что серверные фильтры от DOM XSS не спасают — защита нужна на клиенте.
